# 三险一金合并确认判定规则（当前实现）

> 适用版本：2026-09-10 重构后（commit `0ad6f4e`）
> 术语定义见 [第四节](#四术语与旧版本对照)；历史实证依据见《0申报三险一金合并规则分析.md》（2026-09-08）。
> 本文档描述**代码实际行为**（`tax_merge.py` / `app.py` / 前端弹窗），与 2026-09-10 用户确认口径一一对应。

---

## 一、为什么需要合并确认

同一批报税（同一发放月，如 202608）中，**同一人在多个工资所属月**都有工资单（如 202606、202607 的工资都在 202608 发放）时，报送文件里的三险一金栏填多少需要人工确认：

- **多月**：把各所属月的三险一金**合并上报**（各月之和）。适合上月零申报（上月未报三险）的人。
- **单月**：只报**一个月的三险一金**（取数口径见 [第三节](#三单月取数口径)）。适合上月已报三险（避免重复扣除）的人。
- **不报**：三险一金**全部按 0 上报**（收入照常报）。仅发放月本人确无工资等少见情形，**仅备选、不默认**。

收入（本期收入）**无论选哪种都跨所属月全加**，三险一金的差异只影响养老/医疗/失业/公积金四笔。

## 二、候选判定四场景（核心规则）

> 代码位置：`tax_merge.py::build_merge_suggestions`

对每个跨所属月的人员，先算两个量：

| 量 | 含义 | 计算 |
|---|---|---|
| `cur_insurance` | **发放月**（本次报税发放的月份）的三险一金 | 所属月==发放月的全部工资单四险之和 |
| `insurance_double` | **多月**金额 | 该人全部工资单四险之和 |
| `insurance_single` | **单月**金额 | 见 [第三节](#三单月取数口径)（最近一次三险>0 的所属月全部记录之和） |

然后按四场景判定（`single_equals_double = (insurance_single == insurance_double)`）：

| 场景 | 条件 | 是否弹窗 | 提供的选项 | 「不报」可见 |
|---|---|---|---|---|
| **① 完全自动** | `cur_insurance > 0` 且 `single == double` | **不弹窗**，自动按单月 | — | — |
| **② 当月多笔跨月** | `cur_insurance > 0` 且 `single != double` | 弹窗 | 单月 / 多月 | ❌ |
| **③ 无当月三险、单月==多月** | `cur_insurance == 0` 且 `single == double` | 弹窗 | **报** / **不报** | ✅（报=单月值） |
| **④ 无当月三险、单月!=多月** | `cur_insurance == 0` 且 `single != double` | 弹窗 | 单月 / 多月 / 不报 | ✅ |
| — 全部所属月都无三险 | `insurance_double == 0` | **不弹窗**，不列候选 | — | — |

### 场景解读

- **①**：三险只出现在发放月（当月且仅当月有三险）→ 单月==多月，不存在"合并与否"的选择 → 完全自动不再弹窗。
- **②**：发放月当月就有三险，且还有其他所属月的三险（如 6、7 月工资 8 月发、8 月也有工资单）→ 需选单月（当月的）还是多月合并；当月有工资有险，**谈不到"不报"**。
- **③**：发放月无三险（压月发：8 月发 6/7 月工资，发放当月没有工资单；或当月工资无三险），且三险集中在一笔 → 只有"报不报"的选择，**报=单月值**。
- **④**：发放月无三险、跨月且三险不在一笔（最常见压月发场景）→ 单月/多月/不报三选一。
- 全部所属月都无三险 → 无三险可报，不列候选（零申报走另外的「零申报确认」流程）。

### 判定优先级（先看当月，再比单月/多月）

```
insurance_double == 0              → 不列候选
single == double && cur > 0        → 场景① 自动（不弹窗）
cur_insurance == 0                 → 场景③（single==double）或 场景④（single!=double），能选"不报"
cur_insurance > 0                  → 场景②，不能选"不报"
```

## 三、单月取数口径

> 2026-09-10 用户确认：**最近一次三险>0 的所属月**全部记录之和。

```
单月月份 = 发放月（若发放月有三险）
         └ 否则 = 最近一个「四险之和 > 0」的所属月（按工资所属年月降序找）
单月金额 = 该月份全部工资单的 养老+医疗+失业+公积金 之和
```

- **发放月有三险** → 单月=发放月（场景② 的"当月的单月"）。
- **无当月三险** → 取最近一个有三险的所属月。例：池凤财 202607 发放 5 月工资 → 单月=202605=608.50。
- **全部月份无三险** → 单月三险为 0（此时 `insurance_double == 0`，不列候选）。

> 注意：**不是**"最近所属月"，而是"最近**有三险**的所属月"。某月工资单若四险全 0，会跳过该月找更早的。

生成侧（`merge_records_by_person` 的 `single_certs`）与建议侧（`build_merge_suggestions`）**取数口径完全一致**：收入跨月全加；单月三险 = 最近三险>0 所属月全部记录之和，不累加其他所属月（避免上月已在旧档报过、本月重复扣除）。

## 四、术语与旧版本对照

| 旧术语（<2026-09-10） | 新术语（2026-09-10 起） | 含义 |
|---|---|---|
| 单倍 | **单月** | 只报一个月的三险一金 |
| 翻倍 | **多月** | 各所属月三险合并上报（并非金额×2） |
| （无） | **不报** | 三险一金按 0 上报，仅备选、不默认 |
| 当月 | 发放月 | 本次报税发放的月份（TC8M.ATC8G7） |

**「不报」可见性彻底改为数据判定**：`can_skip = 发放月无三险一金`。2026-09-10 之前曾实现"全局+结算单元两级开关"（commit `1685127`），经用户确认**已移除**（`0ad6f4e`）——开关做法可能误导（是否可"不报"本质取决于数据），把报不报的选择权完全交给用户。

## 五、发薪模式（pay_pattern）

> 配置位置：特殊结算单元配置页 → 发薪模式；存储 `config_db.py::get_pay_pattern_map`（SQLite `special_unit_config.pay_pattern`）

| 值 | 名称 | 含义 | 对建议的影响 |
|---|---|---|---|
| `normal`（默认） | 正常发薪 | 发放月一般有当月工资 | 无，按历史档案判定 |
| `pay_lag` | **压月发** | 发放月无当月工资属正常（如 8 月发的是 6/7 月工资） | 建议=**单月**（最近三险月） |
| `bimonthly` | **双月发** | 隔月发放、每次发两个所属月工资 | 建议=**多月**（报两个月三险之和） |

### 关键约束（2026-09-10 用户确认）

1. 发薪模式**仅影响"建议"与弹窗记号**（`压月发`/`双月发` 徽章），**不跳过弹窗、不控制「不报」**——弹窗仍由用户最终判断。
2. 弹窗处仅做记号展示，**不产生配置、不影响程序逻辑**。
3. 不规则/未配置单元 → 每次由用户判断（`normal` 走历史档案判定）。

### 建议优先级（从高到低）

```
1. BE 强制      ATC93BE≠0（借支/补缴）                  → 单月（high）
2. 发薪模式     pay_lag                                   → 单月（high）
                bimonthly                                → 多月（high）
3. 历史档案     上月有报（三险>0）                        → 单月（high）
                上月未找到                                → 单月（high）
                上月零申报（收入=0 且 三险=0）            → 多月（medium，最需要人工核实）
```

> `ATC93BE` = 补缴及退款保险差额·个人。BE≠0 时 5 月三险已通过收入公式扣除，三险栏不得再合并 → 强制单月（历史实证 40/40 单倍）。

## 六、候选数据结构与前端行为

### 每个候选（candidate）字段

| 字段 | 说明 |
|---|---|
| `can_skip` | 是否可选「不报」（= 发放月无三险，数据判定） |
| `single_equals_double` | 单月==多月（用于场景③与归一化） |
| `pay_pattern` | normal / pay_lag / bimonthly（弹窗徽章：压月发/双月发） |
| `notice` | 提示：`发放月无当月工资单（压月发）` 或 `发放当月工资无三险一金` |
| `insurance_single` / `insurance_double` | 单月 / 多月三险金额（四险分别见 `*_detail`） |
| `suggested` / `reason` / `confidence` | 建议（single/double）+ 理由 + 置信度（high/medium） |
| `default_chosen` / `persisted` | 默认选中（历史持久化优先于建议）/ 是否"已记住" |
| `be_flag` | 行首 ⚠ 标记（ATC93BE≠0，借支/补缴强制单月） |
| `units` / `unit_names` / `main_unit` | 涉及单元与主结算单元（分组依据） |
| `slips` | 全部工资单明细（结算单元-所属月-批次 + 本期收入 + 四险） |

### 前端弹窗行为（`templates/index.html`）

1. **分组**：按主结算单元大组展示（组头：单元名称（代码）·共 N 人），可折叠；每人完整列出发薪工资单明细 + 合计行（本期收入合计 + 当前选择的单月/多月金额，另一模式灰显）。
2. **选项渲染**：
   - 场景②/④：`单月` / `多月`（+ ④ 的 `不报`）；
   - 场景③（`single_equals_double && can_skip`）：渲染为 **`报` / `不报`** 下拉（报=单月值）；`多月`选项被归一化为 `单月`（同步逻辑：`value === 'double' → 'single'`）。
3. **徽章与提示**：`pay_lag` → `压月发` 徽章、`bimonthly` → `双月发` 徽章；`notice` 黄色提示紧邻理由显示；BE 借支行行首 ⚠ + reason。
4. **建议标签**：场景③ 显示 `建议报(单月=多月)·置信度`；其余显示 `建议单月/多月·置信度`。
5. **批量操作**：组级 + 全局。**组级按钮随组内人员选项自动变化**（2026-09-10）：组内全部为场景③（只能 报/不报）时显示 **本组按建议 / 本组报 / 本组不报**（此时"单月/多月"无法覆盖每人的选项，无意义）；否则显示 **本组按建议 / 本组单月 / 本组多月**（组内有人可「不报」时附 **本组不报**）。全局按钮仍为 全部按建议/全部单月/全部多月。「记住本次选择」持久化到下月（黄色「已记住」徽标）。
6. **合计行场景③**：选择为 报 时显示 `报：¥X`（单月==多月，只展示这一值）。
7. **残留选择回退**：`chosen === 'skip' && !can_skip` 时回退到建议值（防御持久化旧值/Excel 导回绕 UI）。
8. **组标签（纯标记提醒）**：组头「标签」按钮可给主结算单元打提醒记号（预设 `压月发`/`隔月发` 或自定义 ≤10 字），仅存 SQLite（`config_db.merge_group_tag`，`/api/merge-group-tags`），**与任何后台逻辑/生成逻辑无关**，下次弹窗自动展示，帮助回忆该组发薪情况。

### Excel 导出/导入（弹窗右上角）

- 导出列：`工资单(结算单元-所属月-批次)` / `姓名` / `证件号` / `职工号` / `主结算单元` / `上月状态` / `建议` / `置信度` / `理由` / `本期收入合计` / `三险-多月` / `三险-单月` / **`选择(单月/多月/不报)`**。
- 导入：按证件号匹配；选择列限 `单月`/`多月`/`不报` 三值，非法文字中止并提示证件号；只作用于本次弹窗，不写库（勾选「记住本次选择」才持久化）。

## 七、生成侧（api_generate）的校验

> 代码位置：`app.py::api_generate`（`merge_by_person` 分支）

```python
skip_certs 校验（2026-09-10 起，纯数据判定，开关已移除）:
  merge_choices 中 mode == "skip" 的人:
    该发放月记录四险之和 == 0   → 允许不报（加入 skip_certs）
    该发放月记录四险之和 > 0    → 忽略该选择（防御 Excel 导回等绕过 UI 的路径）
```

即「不报」只允许**发放月无三险**的人，与服务端建议侧 `can_skip` 一致；这一校验让 Excel 导回等绕过 UI 的路径也无法提交非法"不报"。
