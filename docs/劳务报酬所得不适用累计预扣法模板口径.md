# 劳务报酬所得（不适用累计预扣法）模板口径说明

> 应用模块：模板生成（`laborService`）
> 涉及文件：`app.py`、`queries.py`、`templates_gen/labor_service.py`
> 更新日期：2026-09-07

---

## 一、模板背景

**模板正式名称：劳务报酬所得（不适用累计预扣法）**

- 14 列模板（一行为一人，无校验公式），对应个税申报中的"劳务报酬所得（不适用累计预扣法）"类别。
- 手工参考文件：`07-月劳务报酬所得（不适用累计预扣法）-刘晓澄.xls`（258 人）。
- 模板只针对**劳务报酬（TC90.AAE00P='3'）**人群，不适用于正常工资薪金。

---

## 二、核心口径（手工 258 人文件精确匹配验证）

### 2.1 发放月份 = TC8M.ATC8G7（经办年月），不是 TC93.ATC931（所属月）

**关键结论：手工「07-月」文件按"发放月份"过滤，日期是文件名里的"07-月"（= ATC8G7=202607），
不是工资所属月份（ATC931）。**

```
发放月 202607 的批次 = TC8M WHERE ATC8G7 = 202607 AND ATC8M3 = 2
```

- `ATC8M3`（工资状态）= 2 表示**已确认发放**，是必要条件：`ATC8G7=202607` 下存在
  `ATC8M3=0`（未发放，ATC8M2=0）的批次（如长春中医药大学附属医院等），必须排除。
- 同一发放月批次可横跨多个所属月（ATC931）：松原 04+05、四平 05+06、白山 06+07。
  因此"手工文件的单月/双月合计"差异，本质是**发放月批次跨所属月**，非业务异常。

### 2.2 收入 = SUM(ATC93AA)（工资总额），不是 ATC933（应发工资）

```
收入 = 该发放月全部批次下、按人合计的 ATC93AA（工资总额）
```

- AAE00P='3' 劳务报酬人群的 TC93 记录中 **ATC933（应发工资）恒为 0**（91-93% 记录为 0），
  而 ATC93AA（工资总额）> 0。原实现用 ATC933 会全部填 0（缺陷，已修复）。
- 免税相关字段（ATC936/独生 ATC93W4/采暖 ATC93W21/其他免税 ATC93W33）在该人群全部为 0，
  无扣减项；收入 = 工资总额原始值，不做扣减。

### 2.3 人员范围 = 当前有效 TC90.AAE00P='3'

```
AAE00P='3'（劳务报酬） 且 合同覆盖发放月：
  AAE003 IS NULL OR AAE003 = '' OR AAE003 >= 发放月
```

- 手工 258 人当前有效 AAE00P **全部 = '3'**（0 例外）。
- **期末合同人员必须包含**：如冯守臣 TC90 `AAE003=202607`（费用结束年月 = 发放月 202607，
  非空）——7 月发工资、7 月合同到期，手工文件含此类人员。此前 `AAE003 IS NULL` 判定
  会误排除 27 人（缺陷，已修复）。
- 同一身份证多份合同时，取**费用开始年月（AAE002）最晚**的一份（最后一次生效合同），
  如林淀翔 TC90 有历史 AAE00P='2' 的已终止记录，不能误取。
- **TC90.ATB90R（合同状态）验证（2026-09-07）**：表内确实存在"合同状态"字段，
  界面代码对应表（用户提供）为：
  `1`=暂存、`2`=提交审核、`3`=审核通过（生效）、`4`=审核不通过（打回）、
  `5`=审核通过（终止）。库内分布与之吻合：`'3'`=生效（AAE003 空占 99.9%）、
  `'5'`=终止（AAE003 有值占 97.2%）、`'2'`=少量。**但不能以 ATB90R='3'（生效）
  作过滤**：手工 258 人中有 27 人（冯守臣等）最近且唯一合同 ATB90R='5'（终止，
  AAE003=202607/202608 即发放月）仍须申报（7月发6月工资、合同刚到期）；
  另有 2 人（陈宝、马用祥）存在 3/5 混合合同。AAE003 覆盖判定（空 或 >= 发放月）
  恰好包含这些人员，与手工文件一致，无需改用 ATB90R。

### 2.4 工资总额 > 0 过滤

```
仅保留 工资总额 > 0 的人员（不发钱不申报）
```

- 同一确认批次下 AAE00P='3' 但工资总额 = 0 的人（实测 470 人）不在手工文件中。
  增加该过滤后 confirmed_combos 路径 **258/258 精确匹配、缺 0、多 0、金额差 0**。

### 2.5 按人 + 发放月份合并

- `merge_records_by_person(by_pay_month=True)`：按职工号合并，跨所属月（ATC931）合计收入，
  以 tc930_id 最大记录作为基数。
- Web 主流程经 `confirmed_combos`（前端强制非空）限定批次范围；无 combos 时
  自动按发放月取全部已确认批次（`get_suggestions`），与 Web 组合流程等价。

## 四、实现说明

### 4.1 关键函数

- `queries.py → get_labor_service_cert_numbers(conn, pay_month)`：
  返回 AAE00P='3' 且合同覆盖发放月的身份证号集合（统一大写）。
  SQL：ROW_NUMBER() PARTITION BY AAC002 ORDER BY AAE002 DESC NULLS LAST，取 rk=1。
- `app.py → build_labor_service_records(conn, raw_records, confirmed_combos, month, ...)`：
  confirmed_combos 存在时复用按批次过滤的原始记录；否则按发放月自动取全部已确认批次。
  随后：特殊结算单元过滤（SQLite 配置）→ 按人合并 → **工资总额>0 过滤** → **AAE00P='3' 过滤**。
- `templates_gen/labor_service.py → generate_labor_service`：
  收入列写 `rec.工资总额`；模板名/文件名使用正式名称「劳务报酬所得（不适用累计预扣法）」。
- `queries.py → get_suggestions(conn, pay_month)`：正确口径 `ATC8G7=:pay_month AND ATC8M3=2`，
  当前实现无需修改（2026-09-07 核实）。

### 4.2 各模板月份参数语义对比（易混淆点）

| 函数 | 过滤字段 | 语义 |
|------|---------|------|
| `get_available_months` | TC93.ATC931 | **所属月**（前端 monthSelect） |
| `get_pay_months` | TC8M.ATC8G7 WHERE ATC8M3=2 | **发放月** |
| `get_salary_records` | TC93.ATC931 | 所属月，按单单月取数 |
| `get_suggestions` | TC8M.ATC8G7=pay_month AND ATC8M3=2 | 发放月已确认批次 |

> 陷阱：前端月份下拉框来自所属月（ATC931），但劳务报酬按发放月（ATC8G7）过滤。
> Web 流程中用户确认批次（confirmed_combos）后，系统按批次对应的**各所属月**取 TC93 记录
> （app.py:174-180），再合并，天然支持跨所属月——无需按发放月直接过滤 TC93（TC93 无 ATC8G7 列）。

## 六、待确认事项

1. **双月结算是否为正式业务规则**：吉林银行服务站经理按"双月结算申报"（各单元周期起点不同：
   松原 04-05、四平 05-06、白山 06-07）。当前实现按发放月（ATC8G7）自动覆盖，若后续发现
   部分发放月批次跨超过 2 个所属月，需复核口径。
2. **无 confirmed_combos 的兜底路径**：按全库发放月已确认批次取数（例：202607 有 528 个批次
   含其他单位人群），与手工文件（仅 15 批次）范围不同。Web 主流程前端强制 confirmed_combos
   非空不受影响；CLI/API 直调时需注意。
