# TaxGen 操作指南（日常报税流程）

> 适用版本：master（2026-09-09 及以后）
> 系统入口：`http://<服务器IP>:5000`

本指南面向**日常使用系统的报税操作人员**，按一次完整报税的操作顺序说明每个步骤、
每个按钮/弹窗的含义，以及系统建议与人工决策的边界。

业务规则背后的数据依据见姊妹文档：
[0申报三险一金合并规则分析](./0申报三险一金合并规则分析.md)、
[工资为0不增员不报税规则](./工资为0不增员不报税规则.md)。

---

## 一、一次完整报税流程（速览）

```
选择发放月份 → 搜索批次 → 勾选批次加入待报列表 → 检查合并规则并确认
→ 检查零申报并确认 → 生成报税数据 → 下载文件/查看验证报告
```

| 步骤 | 操作位置 | 目的 |
|------|---------|------|
| 1. 选发放月份 | 主页面顶部「发放月份」下拉框 | 确定本月报送的是哪一批工资（如 2026年07月） |
| 2. 搜索批次 | 搜索区（结算单元名称/所属月份/批次号/经办人） | 列出本月发放的批次（TC8M 汇总） |
| 3. 加入待报列表 | 搜索结果勾选 → 「添加到待报列表」 | 圈定本次报送范围 |
| 4. 检查合并规则 | 待报列表「检查合并规则并确认」按钮 | 处理**跨月发放**人员的三险一金翻倍/单倍 |
| 5. 检查零申报 | 待报列表「检查零申报并确认」按钮 | 处理**本期收入为0**人员的生成/跳过 |
| 6. 生成 | 「生成报税数据」按钮 | 产出 Excel 模板 + 验证报告 |
| 7. 下载/核对 | 生成结果区 | 下载 4 类模板文件 |

> **历史申报库导入（可选，强烈建议）**：首次使用系统时，把上个申报期的
> 个税端导出文件导入「历史申报库」，合并规则判定会更准确。详见[第五节](#五历史申报库-可选但强烈建议)。

## 二、步骤详解

### 2.1 搜索批次并加入待报列表

- **发放月份**：下拉框选择，决定搜索哪个月发放的批次（TC8M.ATC8G7）。
- **搜索条件**：结算单元名称（模糊）、所属月份（YYYYMM）、批次号、经办人，均为可选。
  - **「仅已发放」**复选框默认勾选：只显示状态为"已发放"（ATC8M3=2）的批次，即实际可报送的。
- 点「搜索」后结果按结算单元分组列出：结算单元、发放月份、所属月份、批次、状态、人数、合计收入。
- **勾选要报送的批次 → 点「添加到待报列表」**。
  - `结算单元 + 所属月份 + 批次` 三元组是系统的最小报送单位，称为一个"组合"。
- 待报列表可进一步筛选（按所属月/结算单元/批次）、全选/取消全选、删除选中。

**注意**：多次搜索可累计添加。若一单元有多笔所属月工资（如 5 月工资与 6 月工资都在 7 月发放），
应**全部加入**待报列表，这正是跨月合并检查的前提。

### 2.2 检查合并规则（三险一金合并规则确认）

**什么情况会出现这个弹窗**：同一人在待报批次中跨了多个**所属月**（如 5 月工资与 6 月工资同在
7 月发放）。此时该人的三险一金在报送文件中是"单倍"（只报 6 月）还是"翻倍"
（5 月+6 月三险合并填入）需要人工确认——这就是历史上手工报税时的判断点。

**操作**：
1. 确认待报列表中**勾选了本次要报送的批次**（未勾选的批次不参与检查）。
2. 点「检查合并规则并确认」。弹出《三险一金合并规则确认》：
   - 副标题显示：`202607 发放 → 上月档 202605`（本次报送范围的最早所属月 = 上月档）。
   - 表格列出每个**跨月人员**：姓名、证件号、涉及结算单元、所属月、上月档案状态、
     系统建议（翻倍/单倍）、置信度、理由、以及最终选择下拉框。
3. 为每人选定「翻倍」或「单倍」：
   - **逐个**调整右侧下拉框；
   - 或使用批量按钮：**全部按建议**（推荐）/ **全部翻倍** / **全部单倍**。
4. （可选）勾选「**记住本次选择（持久化到配置）**」——本次选择存入本地配置，
   下月同一人再次出现时默认沿用（表格中带黄色「已记住」徽标）。
5. 点「确认并关闭」。待报列表出现绿色标记「已确认 N 人合并规则」。

**系统建议的依据与置信度**：

| 上月档案状态 | 系统建议 | 置信度 | 理由 |
|-------------|---------|--------|------|
| 上月**有报**（三险>0） | 单倍 | 高 | 三险已在累计专项扣除中体现，翻倍会虚增扣除 |
| 上月**零申报**（收入=0 且三险=0） | **翻倍** | 中 | 61% 历史实证翻倍，但存在例外，**务必人工核实** |
| 上月**未找到**（档案中无此人） | 单倍 | 高 | 历史 0 例翻倍；多属特殊单元本月也不报 |
| 本月 **ATC93BE≠0**（借支/补缴，行首有 ⚠ 红色标记） | 单倍 | 高 | 三险已通过借支在收入侧扣除，翻倍=重复扣除（**建议不可改**，属数据事实） |

> - 置信度颜色：高=绿、中=黄、低=红。标黄的"翻倍"建议最需要人工核实。
> - 上月档案状态来自历史申报库（税款计算类型）；**未导入历史数据时全部判"未找到"→ 单倍**，
>   系统可用、判定保守，不导入也不会报错（详见第五节）。
> - ⚠BE借支行：系统仍给出单倍建议（理由"建议不可改"），如确有特殊情况需翻倍，
>   可在下拉框中手动改选——系统只做事实提示，最终以你的选择为准。

### 2.3 检查零申报（本期收入为0人员）

**什么情况会出现这个弹窗**：待报批次中存在**本期收入为0**但出现在工资单中的人员。
这些人是否需要生成零申报记录，需要确认（部分结算单元规则默认不生成）。

**操作**：
1. 点「检查零申报并确认」。弹出《零申报确认》。
   - 副标题：`本月共 N 条本期收入为0的记录，M 个结算单元`。
   - 按结算单元分组卡片，组头显示：单元名称/代码、配置徽标（`配置不申报`=特殊配置，
     `普通单元`=无配置）、共 N 条/合计金额。
   - 组内每行代表一个人：本期收入、**建议（生成/不生成）**、理由、选择下拉框。
2. 确认方式：
   - **整行逐个**调整下拉框；
   - **批量**：三个全局按钮（全部按建议/全部生成零申报/全部不生成）；
   - **按单元**：每个卡片右上角也有三个按钮（按建议/全部生成/全部不生成），
     适合"某单元全部不生成、其余单元全部生成"的批量操作。
3. （可选）勾选「记住本次选择」持久化到配置。
4. 点「确认并关闭」。出现绿色标记「已确认 N 人零申报」。

**建议逻辑**：

| 场景 | 建议 | 理由 |
|------|------|------|
| 结算单元配置了「工资为0不增员不报税」 | 不生成 | 该单元人员工资为0时不报税 |
| 普通结算单元 | 生成 | 本期收入为0，默认生成零申报 |

> 若在「特殊结算单元配置」页配置过完全排除单元（`exclude_all`），这些人**不会出现在**弹窗中，
> 直接不生成（见[第七节](#七特殊结算单元配置)）。

### 2.4 生成报税数据

点「生成报税数据」前，确认以下几点：

- **合并多条工资记录**（默认勾选）：同一人多笔工资合并为一行。
  - **按人+发放月份合并**（默认）：每人一行，本期收入/五险一金/个税**全部合计**
    （跨月合并场景下，翻倍的三险在此体现）。
  - **按人+所属月份合并**：同人同月多笔合并，同一人可能多行。
- **年平均工资总额**（默认 120000 元）：用于验证报告判断解除劳动合同一次性补偿金
  是否达到 3 倍年平均工资的交税标准，按当地口径调整。
- 若已做过合并规则/零申报确认，选择会自动带入（生成接口使用确认结果）。

点「生成报税数据」→ 等待生成（批次多时约 2-10 秒）→ 结果区显示 4 类文件：

| 模板 | 内容 |
|------|------|
| 正常工资薪金所得 | 30 列主表，含验证公式 |
| 劳务报酬所得 | 14 列 |
| 全年一次性奖金收入 | 11 列（仅奖金>0 记录） |
| 人员信息采集导入模板 | 51 列，自动解析身份证性别/出生日期 |

结果表的**验证通过/验证失败**统计：失败通常因应发工资=0 但实发≠0（非正常工资薪金类），
可在验证报告（`/api/validate/<月份>`）中查看失败明细并核对。

## 三、速查：如果要跳过某一步

| 场景 | 可以跳过？ | 影响 |
|------|-----------|------|
| 不点「检查合并规则」直接生成 | 可以 | 跨月人员按单倍处理（不合并三险），可能漏报 5 月三险 |
| 不点「检查零申报」直接生成 | 可以 | 本期收入为0人员**按普通规则全部生成**零申报（若配置了不申报单元则仍跳过） |
| 不导入历史申报库 | 可以 | 合并规则全部判"上月未找到"→ 单倍（保守，不虚增） |
| 不勾选"合并多条工资记录" | 可以 | 每人每笔一行（不合并），文件行数增多 |

## 四、常见问题（FAQ）

**Q1: 点「检查合并规则」一直显示"检查中..."是死机了吗？**
一般不是。跨多所属月、多批次时检查需要几秒（历史版本曾高达 30 秒，2026-09-09 优化后
全量 528 组合约 2 秒）。若超过 30 秒仍无响应，查看服务日志 `logs/taxgen.log` 找异常堆栈。

**Q2: 要不要导入历史申报数据？**
**不是必须**。未导入时系统判定保守（上月"未找到"→ 单倍），可正常完成整个流程。
但导入后：
- 上月**零申报**的人会得到"翻倍"建议（61% 实证），避免漏报三险；
- 上月**有报**的人会明确"单倍"，避免虚增扣除。
建议在系统上线初期一次性导入上个申报期文件（见第五节）。

**Q3: 程序建议一定是正确的吗？**
**不是**。系统是"建议工具":给你提示 + 理由 + 置信度，**最终每个人员的翻倍/单倍、
零申报生成/跳过都由你在弹窗中确认**。标黄（置信度=中）的"翻倍"建议最需人工核实——
历史数据显示 61% 翻倍、其余 39% 是其他情况。

**Q4: 上月有报的人，系统建议单倍、我能改成翻倍吗？**
能。系统建议仅供快速处理，下拉框允许改选任意值。但请知悉翻倍会导致三险重复扣除
（上月档已报过），一般不建议。⚙ 唯一的例外提示是 ATC93BE≠0 标记——那是数据事实
（三险已借支扣除），系统用红色 ⚠ 提醒，但仍允许你改。

**Q5: "记住本次选择"是什么意思？**
把该人员的翻倍/单倍、零申报生成/跳过选择永久存入本地配置（SQLite）。下月该人再次
跨月/零申报时，下拉框默认选中记忆值并带「已记住」徽标。取消勾选则不记忆，只生效本次。

**Q6: 一个单元有多个月份的工资（都在本月发放），怎么处理？**
全部加入待报列表 → 点「检查合并规则」→ 跨月人员会全部列出并逐人确认 →
生成时选"按人+发放月份合并"。这正是跨月合并的标准流程。

**Q7: 验证报告里有很多"验证失败"怎么办？**
多数"失败"是"应发工资=0 但实发≠0"的非正常工资薪金类记录（劳务/补偿类），
不是数据错误。看具体原因分类后，异常的再去工资系统核实。

**Q8: 生成的文件和手工报的数对不上？**
先核对：1) 待报列表是否**包含全部**相关批次（漏批次=少人）；2) 合并规则弹窗是否已确认
（未确认的跨月人员按单倍，可能少三险）；3) 合并粒度选的是"发放月合并"还是"所属月合并"。

## 五、历史申报库（可选但强烈建议）

**入口**：主页面右上角「历史申报库」。

**作用**：保存税务局个税端导出的历史申报文件，供**合并规则判定**（上月"有报/零申报/未找到"）
和**回盘比对**使用。数据存本地 `tax_return.db`（SQLite），不写 Oracle。

**导入步骤**：
1. 税务局个税端 → 查询历史申报记录 → 导出 Excel 文件。
2. 历史申报库页 → 选择文件（可多选）→ 上传。
   系统按**表头自动识别** 4 类文件（与文件名无关）：
   - 税款计算（特征列：税款所属期起）
   - 正常工资薪金（特征列：累计子女教育）
   - 劳务报酬（特征列：允许扣除的税费）
   - 全年一次性奖金（特征列：全年一次性奖金额）
3. 导入结果逐文件显示：识别类型、记录数、所属月份。单文件失败不影响其他文件。

**必读**：
- 合并规则判定只用 **税款计算** 类（字段含本期收入 + 四险一金）。
- 建议导入**最近 1-2 个申报期的税款计算文件**即可覆盖合并判定需求。
- 同人同月同类型重复导入会自动覆盖（upsert），放心重复导入。

## 七、特殊结算单元配置

**入口**：导航栏「特殊结算单元配置」。

两种模式（互斥，见 [工资为0不增员不报税规则](./工资为0不增员不报税规则.md)）：

| 模式 | 含义 | 影响 |
|------|------|------|
| **工资为0不增员不报税** | 该单元人员**本期收入合计=0**时，不增员、不报税 | 有收入仍正常报税；影响增减员比对 + 零申报建议 |
| **完全排除不增员不报税** | 该单元**不论是否发工资**一律不增员不报税 | 从根源排除；人员不会出现在任何建议弹窗 |

操作：新增（代码可留空按名称匹配）→ 打开对应开关 → 重新生成增减员比对表/零申报检查。

## 八、部署与运维（管理员）

```bash
sudo systemctl status taxgen     # 状态
sudo systemctl restart taxgen    # 重启（代码更新后执行）
sudo journalctl -u taxgen -f     # 实时日志
```

- 应用日志落盘：`logs/taxgen.log`（按 5MB 轮转，保留 3 份），API 异常含完整堆栈。
- 配置：`.env`（数据库连接、`DB_POOL_MIN`/`DB_POOL_TIMEOUT` 连接池参数）。
- 数据库安全：Oracle 业务库**只读**；所有业务配置、历史申报、回盘数据存本地 SQLite。
